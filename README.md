# Scripture

**the language of the machine gods**
LLM-first systems language experiment

Scripture is an attempt at a programming language where the target audience is an LLM. Humans are second-class citizens by design, where tooling is used to improve readability.

As LLM coding technology continually progresses, coding by hand is becoming less and less feasible economically. However the issues of LLMs hallucinating patches, silently mutating unrelated code, and generally lying about purity / safety / side effects cause real problems in code quality generated by LLMs.

Scripture's bet:

* if you give the model an IR-shaped language instead of a "human ergonomic" language,
* and you force it to declare intent and effects explicitly,
* and you validate its output before it ever touches disk,

you can actually trust machine-written code.

This repo is the first draft of that language.

Name note: "Scripture" is a Terry Davis shout-out, pour one out for the GOAT

## Core goals

1. **LLM-native**
   The source of truth is a structured, tag-based syntax that looks more like serialized AST than C/Rust/Python. Humans can get a pretty view rendered on top, but the canonical form is machine-structured text, not freeform code.

2. **Deterministic edit surfaces.**
   Instead of “rewrite this whole file,” we let the model rewrite *just the body of a method* or *just a block*, in-place, in a way that's mechanically spliceable. No blind diffs. No guessing what changed.

3. **Side effects are explicit.**
   Mutation, IO, allocation, external calls — these are not implicit in clever syntax. They are their own nodes. If something mutates state, you can literally grep for it.

4. **Static validation as a gate.**
   We will build a validator that checks any LLM output before it can land:

   * Are all tags closed and legal?
   * Are you declaring purity and then violating it?
   * Are you mutating something in a block that said it wouldn't mutate?
     If the answer is “yes, you're lying,” the output is rejected. The model can fix and retry, but garbage never hits the repo.

5. **Eventual low-level control.**
   We want C-class control: deterministic execution, manual layout, ability to talk to hardware. Pointers are a TODO below, but they’re in scope.

## High-level shape

Scripture code is made of nested tagged blocks with attributes. Think "XML but it's actually your AST" — except this isn't markup around a language. This *is* the language.

Basic unit types:

* `<class>` to define data + methods
* `<field>` for members
* `<method>` for behavior
* `<params>` / `<param>` for parameters
* `<body>` for executable code
* Structured statements inside `<body>` like `<let>`, `<assign>`, `<if>`, `<while>`, `<return>`, etc.

There is no freeform "just write some C in here". Every statement is a node. Every node advertises what it's doing.

That means:

* we can parse it trivially
* we can diff it structurally
* an LLM can regenerate just the `<body>` of a method without touching the signature

This is intentional.

## Example: a tiny data type with a mutating method

```txt
<class name=Pair visibility.PUBLIC>
    <fields>
        <field name=m1 type=i32 mutable/>
        <field name=m2 type=i32 mutable/>
    </fields>

    <methods>

        <method name=swap return=VOID purity.MUTATING safety.SAFE>
            <params>
                <param name=self type=Pair mutable/>
                <param name=other type=Pair mutable/>
            </params>

            <body>
                <let name=tmp type=i32>
                    <expr>self.m1</expr>
                </let>

                <assign target_object=self target_field=m1>
                    <expr>other.m1</expr>
                </assign>

                <assign target_object=other target_field=m1>
                    <expr>tmp</expr>
                </assign>

                <let name=tmp2 type=i32>
                    <expr>self.m2</expr>
                </let>

                <assign target_object=self target_field=m2>
                    <expr>other.m2</expr>
                </assign>

                <assign target_object=other target_field=m2>
                    <expr>tmp2</expr>
                </assign>
            </body>
        </method>

    </methods>
</class>
```

Read it literally:

* `Pair` has two fields, both mutable 32-bit ints.
* `swap` is a method that takes two `Pair`s by mutable access and swaps their contents.
* `purity.MUTATING` says: this method is allowed to modify state.
* `safety.SAFE` says: this is not doing any explicitly dangerous / low-level operations. (We'll get to `safety.UNSAFE` later when we add raw pointer ops.)

Inside `<body>`: every effect is spelled out.

* `<let>` introduces a new value.
* `<assign>` mutates a field on an object.
* `<expr>` is a pure expression. More on that below.

There is no ambiguity. There's nowhere to hide side effects.

Human readable pretty-print would look something like:

```
public class Pair {
    m1: i32;
    m2: i32;

    mutating fn swap(self: &mut Pair, other: &mut Pair) -> void {
        let tmp: i32 = self.m1;
        self.m1 = other.m1;
        other.m1 = tmp;

        let tmp2: i32 = self.m2;
        self.m2 = other.m2;
        other.m2 = tmp2;
    }
}
```

Work flow from a humans perspective would be:

* Prompt changes to the code
* LLM creates structured diffs, updates
* Human previews code in a Rust/C like syntax
* BUT, low level AST tag based syntax is human readable enough

Coding is a dialogue between the man and the machine, and the code is structured to play to the strengths of both

## Attribute conventions

Short answer: **No — don’t use string literals for fixed-vocabulary parameters.** Use atoms/enums (unquoted) or presence flags. Reserve quoted strings for truly free text.

Why we avoid quoted enums:

* Fewer failure modes — no smart quotes, dropped quotes, or mismatched casing.
* Sharper tokens — `purity.MUTATING` is easier to visually scan than `"mutating"`.
* Validator clarity — membership checks are trivial when the vocabulary is unquoted atoms.
* Style drift control — atoms make it harder to invent `"mutatiing"` or `"pure-ish"`.

### Recommended conventions

* **Enums as atoms (unquoted):**
  * `purity=PURE | MUTATING | IO`
  * `safety=SAFE | UNSAFE`
  * `visibility=PUBLIC | PRIVATE`
* **Booleans as presence flags (default = false):**
  * `mutable` (present → true, absent → false)
  * If you have to spell false explicitly, tolerate `mutable=false` but don’t encourage it.
* **Types and identifiers as atoms:** `type=i32`, `type=Pair`, `name=swap`.
* **Free text gets quotes:** `doc="Compute checksum of payload"`.

### Preferred: namespaced presence flags

To avoid `=` entirely for enums, we treat each option as a namespaced flag. Exactly one flag from each enum group must appear; the validator rejects zero or multiple selections.

```txt
<method name=swap return=VOID purity.MUTATING safety.SAFE>
    <params>
        <param name=self type=Pair mutable/>
        <param name=other type=Pair mutable/>
    </params>
    <body> ... </body>
</method>
```

### Canonicalization during the transition

* The parser can accept legacy string forms for a short window (e.g. `purity="mutating"`, `mut="true"`).
* The formatter normalizes everything back to atoms/flags and emits a warning so authors migrate.
* After the first milestone, reject string-valued enums outright.

### Tiny before/after

Avoid:

```txt
<field name="m1" type="i32" mutable="true"/>
<method name="swap" return="void" purity="mutating" safety="safe">
```

Prefer:

```txt
<field name=m1 type=i32 mutable/>
<method name=swap return=VOID purity.MUTATING safety.SAFE>
```

## Purity / safety model

Scripture does not pretend everything is magically safe. We don't lie to ourselves that the compiler will infer intent.

We make you say it out loud:

* `purity.PURE`:
  This method promises not to mutate anything and not to perform IO. Think "mathematical function."

* `purity.MUTATING`:
  This method can update state (write to fields, reassign values).

* (later) `purity.IO`:
  This method is allowed to talk to the outside world, log, allocate, free, etc.

* `safety.SAFE` vs `safety.UNSAFE`:
  `safety.SAFE` means "no raw pointer tricks, no manual memory shenanigans, no UB-tier behavior."
  `safety.UNSAFE` is where we let you pull out the knives (pointer arithmetic, manual free, etc.) — TODO, not implemented in the first draft grammar but explicitly planned.

Why do this? Because now you can ask the LLM:

> "Give me a safe pure function that computes a checksum, no IO, no mutation."

and it has a slot to put that promise: `purity.PURE safety.SAFE`.

Then, critically, the validator can reject anything that violates it before it lands in git.

## Statements

Inside a `<body>`, you don't freehand code. You emit structured statements. Early core set:

### `<let>`

Create a new local binding.

```txt
<let name=tmp type=i32>
    <expr>self.m1</expr>
</let>
```

That is: `let tmp: i32 = self.m1;`

* `name` is the symbol you're introducing in this scope.
* `type` is explicit. No inference hand-waving.
* The contents are either `<expr>` (pure expression, see below) or a `<call>` that returns a value.

---

### `<assign>`

Write to an object's field.

```txt
<assign target_object=self target_field=m1>
    <expr>other.m1</expr>
</assign>
```

That is: `self.m1 = other.m1;`

A few things to notice:

* We are not doing clever surface syntax like `self.m1 = other.m1;`.
  We explicitly spell out that this is an assignment to a *field of an object*, which is a side effect.
* Assignments are statements. You cannot hide them inside `<expr>`.

This matters because purity analysis becomes trivial. If you see `<assign>`, you know it's mutating. The model can't sneak in a mutation.

---

### `<return>`

Return a value (or not).

```txt
<return/>
```

or

```txt
<return>
    <expr>tmp + 1</expr>
</return>
```

Again: structured. Obvious to parse. Obvious to diff.

### Control flow (draft)

Not yet fully nailed down, but directionally:

```txt
<if>
    <cond><expr>a < b</expr></cond>
    <then>
        ...statements...
    </then>
    <else>
        ...statements...
    </else>
</if>
```

```txt
<while>
    <cond><expr>i < n</expr></cond>
    <body>
        ...statements...
    </body>
</while>
```

It's boring on purpose. Boring is good. Boring is predictable. Predictable is reliable.

## Expressions: the `<expr>` sublanguage

Expressions in Scripture are intentionally *small*.

The rule is:
**`<expr>` is pure. No side effects. No mutation. No IO.**

Allowed inside `<expr>`:

* integer / bool / string literals
* local variable names (`tmp`, `count`, etc.)
* field access (`self.m1`, `other.m2`)
* arithmetic (`+ - * / %`)
* comparisons (`< <= > >= == !=`)
* boolean ops (`&& || !`)
* parentheses for grouping

Example:

```txt
<let name=sum type=i32>
    <expr>self.m1 + other.m1</expr>
</let>
```

```txt
<if>
    <cond><expr>self.m1 == other.m1 && self.m2 == other.m2</expr></cond>
    <then>
        <return/>
    </then>
    <else>
        <body>
            <assign target_object=self target_field=m1>
                <expr>other.m1</expr>
            </assign>
        </body>
    </else>
</if>
```

Why is `<expr>` restricted like this?

Because we want to be able to run a validator that:

* parses `<expr>` with a tiny deterministic parser,
* proves it's side-effect-free,
* and rejects anything that isn't legal arithmetic / reads / comparisons.

That validator is the choke point. Scripture doesn't trust the LLM. Scripture asks it what it *intends*, and then either accepts the program or bounces it.

This is one of the big differences vs "prompt engineering a normal language." Scripture is not about vibes. It's about giving the model no room to hide behavior.

## Calls (planned but coming fast)

We are going to support calls like this:

```txt
<call name=magnitude expect=i32 purity.PURE>
    <arg><expr>self.m1</expr></arg>
    <arg><expr>self.m2</expr></arg>
</call>
```

This returns a value, and can appear inside `<let>` in place of `<expr>`.

Why not let the model inline `magnitude(self.m1, self.m2)` directly into `<expr>`?
Because we don't want `<expr>` to become a trojan horse for side effects.

Even if `magnitude` is logically pure, we still force the call to be spelled out in a `<call>` node with `purity.PURE` declared. That gives us two things:

* We can reject any call marked pure if its callee isn't actually pure.
* We can track purity boundaries statically.

Later we'll also allow impure calls:

```txt
<call name=log_info purity.IO>
    <arg><expr>"swapping pairs"</expr></arg>
</call>
```

Those are statements, not values. You can't sneak them into `<expr>`.

## Safety and low-level control

Each method advertises a `safety` level:

```txt
<method name="swap" return="void" purity="mutating" safety="safe">
    ...
</method>
```

* `safety.SAFE` means you're not doing raw pointer tricks, direct memory arithmetic, manual free, etc.
* In the future we'll support `safety.UNSAFE` to explicitly allow knife-fight behavior: manual allocation, pointer arithmetic, alias-heavy mutation of shared memory, etc.

That tiering is important. We *do* want C-class power. We just want it quarantined and labeled so we can:

* audit it cleanly,
* diff it cleanly,
* and tell the model "write the safe version first, then write the unsafe accelerated version under a new method."

## What Scripture is *not*

* It's not "XML that we later convert to Rust."
  Scripture *is* the canonical source. Human readable code is a compilation target.

* It's not "a nicer prompt."
  This is not prompt engineering. This is an attempt to define a language that an LLM can (1) generate deterministically, (2) be validated against hard rules, and (3) be compiled.

* It's not "human friendly first."
  We will absolutely build a pretty-printer / IDE view that makes this look like normal code. But humans do not get to break the canonical structure. If you hand-edit the pretty layer and it can't map back to valid Scripture, it gets rejected. Humans are encouraged to *ask the model* to make structural changes, but the IR layer is also structured in a way that humans can modify it as needed.

## Why this might actually work

LLMs are already frighteningly good at producing structured JSON for a known schema. They're also good at imitating tree-shaped patterns when the tree is explicit and repetitive.

They are less good at:

* maintaining diff-style patches across multiple hunks,
* keeping track of who mutates what,
* remembering to close braces,
* never silently changing unrelated lines,
* not lying about what is "pure."

Scripture is built to lean into what they're already good at (structured repetition) and fence off what they're bad at (implicit side effects, slippery syntax, state hidden in clever operator sugar).

## Roadmap (initial)

1. Freeze the minimal core tag set:

   * `<class>`, `<fields>`, `<field>`, `<methods>`, `<method>`
   * `<params>`, `<param>`
   * `<body>`
   * `<let>`, `<assign>`, `<return>`, `<if>`, `<while>`
   * `<expr>`
   * `<call>`
2. Write a validator that:

   * verifies tag structure and allowed attributes
   * parses `<expr>` and rejects anything with side effects
   * checks purity vs body contents (`purity.PURE` means: no `<assign>`, no IO calls, etc.)
   * checks safety vs body contents (`safety.SAFE` means: no pointer ops once we add them)
3. Write a dumb codegen pass from Scripture -> Rust/C-ish output (doesn't have to be optimal; just has to run)
4. Wire the LLM loop:

   * prompt model with current Scripture snippet
   * ask it to rewrite only a targeted `<body>` or generate a new `<method>`
   * validate output
   * auto-splice if valid

At that point we have something real.
